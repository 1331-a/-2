# 第一部分：`bot.py`（平台交互层，237 行）

## 1.1 全局常量与工具

```python
_ACT_TO_RESPONSE = {"fold": -1, "allin": -2, "call": 0, "check": 0}
```
**逐行解释**：一个**字典**，把内部动作用的名字映射成平台要求的整数。
- `"fold"`（弃牌）→ `-1`
- `"allin"`（全押）→ `-2`
- `"call"`（跟注）/ `"check"`（过牌）→ 都是 `0`（平台用同一个 0 表示"不加注"）
- 加注（`"raise"`）不在表里，因为它的数字是**变量**（加注后的总注额）。

```python
_LAST_HAND = [None]        # 用单元素列表当"可变全局"（函数里改得动）
```
**为什么用列表而不是 `_LAST_HAND = None`？**
因为函数内要修改它。若写成普通变量，函数里赋值会变成"新建局部变量"，
必须写 `global`。用列表 `lst[0] = x` 是"改内容"而非"重新绑定"，不需要 `global`。
这是一个常见的小技巧。

```python
def _log(msg):
    """诊断输出 —— 必须写 stderr（stdout 是平台协议通道）。"""
    try:
        import sys as _sys
        _sys.stderr.write(msg + "\n")
        _sys.stderr.flush()
    except Exception:
        pass
```
**逐行**：
- `import sys as _sys`：函数内导入（局部导入），避免模块级污染。
- `_sys.stderr.write(...)`：写**标准错误**。**关键**：`stdout` 是平台的协议通道，
  往里写日志会被平台当成"回复"→ 解析失败 → 判负。
- `.flush()`：立刻推出去，别留在缓冲区。
- `try/except`：日志失败也绝不能影响主流程。

## 1.2 动作 → 整数：`_to_response()`

```python
def _to_response(action):
    """把内部动作 dict 转为 response 整数。"""
    act = action.get("act", "fold")          # ① 取出动作名；缺省当弃牌（最保守）
    if act == "raise":                       # ② 加注要单独处理
        try:
            num = int(action.get("num", 0))  # ③ 取加注后的"本轮总注额"
        except (TypeError, ValueError):
            return -1                        # ④ 取不出来 → 弃牌（保守）
        return num if num > 0 else -1        # ⑤ 非正数无意义 → 也弃牌
    return _ACT_TO_RESPONSE.get(act, -1)     # ⑥ 其余动作查表；未知动作 → 弃牌
```
**关键变量**
| 变量 | 含义 |
|---|---|
| `action` | 决策层返回的字典，如 `{"act": "raise", "num": 300}` |
| `num` | **raise-to 语义**：不是"加多少"，而是"加完后我这轮总共下注多少" |

**为什么这么写**：`get(act, -1)` 的兜底很关键——
万一决策层返回了个 `{"act": "blah"}`，这里会退化成弃牌，而不是让平台收到非法值。

## 1.3 第二道安全网：`_final_guard()`

```python
def _final_guard(state, resp):
    """整数 response 层面的最后一道安全网，绝对保证合法。"""
    try:
        to_call = state.to_call      # ① 我还需要跟多少（0 = 可以过牌）
        my_left = state.my_left      # ② 我还剩多少筹码

        if resp == -1:               # ③ 弃牌
            return -1 if to_call > 0 else 0
```
**③ 解释（重要）**：原始写法是"弃牌永远合法"，**这是错的**。
当 `to_call == 0`（对方没下注）时，你**不能弃牌**——只能过牌。
返回 `-1` 会被平台拒收，甚至 fallback 成别的动作（可能是加注）。
所以：需要跟注才能弃；不需要跟注就必须改成 `0`（过牌）。

```python
        if resp == -2:                       # ④ 全押
            if my_left > 0:
                return -2                    #    还有筹码 → 全押合法
            return -1 if to_call > 0 else 0  #    没筹码了 → 退化成弃/过

        # 规则5：本局有人全押 → 只能弃牌(-1)/全押(-2)
        if state.any_allin:
            return -2 if my_left > 0 else -1
```
**④/规则5 解释**：本手只要出现过 all-in，平台就只接受两种动作。
这是规则层面的硬约束，所以放在这里"一刀切"。

```python
        if resp == 0:                        # ⑤ 跟注 / 过牌
            if to_call <= 0:
                return 0                     #    无需跟注 → 过牌合法
            if my_left > to_call:
                return 0                     #    筹码够 → 跟注合法
            return -2                        #    筹码不够完整跟 → 只能全押
```
**⑤ 注意 `> to_call` 而不是 `>=`**：平台要求"跟注后剩余筹码必须严格大于 0"，
即 `my_left - to_call > 0`。等于时会判非法。

```python
        num = int(resp)                      # ⑥ 加注
        if num <= 0:
            return -1
        min_r = state.min_raise()            #    最小加注（本轮最大注的 2 倍）
        max_r = state.max_raise()            #    最大加注（留出跟注空间）
        if num < min_r:
            num = min_r                      #    太小 → 抬到最小
        if num >= max_r or num >= my_left:
            return -2                        #    太大 → 直接全押
        return num
    except Exception:
        return -1                            # ⑦ 任何异常 → 弃牌（最保守）
```
**⑥ 解释**：加注数被"夹"到合法区间。超上限时不报错，而是转成全押——
全押永远是合法的进攻动作，比返回一个越界数字安全。

## 1.4 异常兜底：`_fallback_resp()`

```python
def _fallback_resp(state):
    """决策层异常时的保守动作：能过牌就过牌，能跟就跟，否则弃牌。"""
    try:
        if state.any_allin:
            return -1                      # ① 有人全押 → 不跟，弃牌
        if state.to_call <= 0:
            return 0                       # ② 不用跟 → 过牌（免费看牌）
        if state.my_left > state.to_call:
            return 0                       # ③ 跟得起 → 跟注
        return -1                          # ④ 都做不到 → 弃牌
    except Exception:
        return -1                          # ⑤ 连状态都读不了 → 弃牌
```
**设计理念**：这是"决策层抛异常"时的救生圈。优先级是
**过牌 > 跟注 > 弃牌**——因为过牌/跟注不会立刻输掉这一手，而弃牌会。

## 1.5 取本轮请求：`_extract_request()`

```python
def _extract_request(obj):
    """从 BotZone JSON 交互输入中取出本轮 request dict（可能为 None）。"""
    reqs = obj.get("requests") or []        # ① 取数组；缺失/None → 空列表
    for item in reversed(reqs):             # ② 从最后一个往前遍历（最新在最前）
        cand = item
        if isinstance(cand, str):           # ③ 有时元素是 JSON 字符串，要再解析
            try:
                cand = json.loads(cand)
            except Exception:
                continue                    #    解析不了 → 试下一个
        if isinstance(cand, dict) and ("my_cards" in cand or "history" in cand):
            return cand                     # ④ 找到"看起来像牌局请求"的就返回
    return None                             # ⑤ 都没找到 → None（上层走保守分支）
```
**关键变量**：`reversed(reqs)` 让最新的请求排在最前，取到就返回。

## 1.6 持久化字符串：`_persisted_str()`

```python
def _persisted_str(v):
    if isinstance(v, str):     # ① 已经是字符串 → 直接用
        return v
    if v is None:              # ② None → 空串
        return ""
    try:
        return json.dumps(v)   # ③ 是对象 → 序列化成字符串
    except Exception:
        return ""              # ④ 序列化失败 → 空串（宁可丢记忆，不能崩）
```

## 1.7 单轮调度：`_handle_line()`

```python
def _handle_line(obj):
    """处理一行 JSON 输入，返回 (resp, data_out, json_mode)。"""
    json_mode = False
    data_str = gdata_str = ""
    request = None

    if isinstance(obj, dict) and "requests" in obj:      # ① 平台包装格式
        json_mode = True
        data_str = _persisted_str(obj.get("data"))
        gdata_str = _persisted_str(obj.get("globaldata"))
        request = _extract_request(obj)
    elif isinstance(obj, dict) and ("my_cards" in obj or "history" in obj):
        request = obj                                    # ② 本地调试：裸 request

    resp = 0
    data_out = ""
    try:
        if request is None:
            resp = 0                    # ③ 拿不到状态 → 交过牌（最保守）
        else:
            state = parse_request(request)               # ④ 解析协议 → 状态对象
            try:
                model = OpponentModel.from_json(gdata_str or data_str)   # ⑤ 恢复记忆
                build_model_from_history(model, request, state)          # ⑥ 增量更新
                ctx = MatchContext.from_dict(model.ctx_dict)             # ⑦ 赛制上下文
                ctx.update(state)                                        #    结算上一手
                ctx.sync_baseline(state)                                 #    同步激进档
                ...
                action = decide(state, model, ctx, debug=_dbg)           # ⑧ 决策
                _raw = _to_response(action)                              # ⑨ 转整数
                resp = _final_guard(state, _raw)                          #    合法性校验
                model.ctx_dict = ctx.to_dict()                            #    存回记忆
                data_out = model.to_json()
            except Exception:
                resp = _fallback_resp(state)   # ⑩ 决策链任何异常 → 保守动作
    except Exception:
        resp = 0                               # ⑪ 连解析都失败 → 交过牌
    return resp, data_out, json_mode
```
**逐行要点**
| 行 | 说明 |
|---|---|
| ⑤ | `from_json(gdata_str or data_str)` —— 优先用 globaldata，缺失时退回 data |
| ⑥ | 用本手完整 history 增量更新对手统计（内部有去重游标）|
| ⑦ | 从 `model.ctx_dict` 恢复赛制上下文（第几手、领先多少、激进度）|
| ⑧ | ★ 决策核心，返回 `{"act": ...}` |
| ⑨ | 转成整数 → 过 `_final_guard` |
| ⑩ | **任何**异常都不外抛，退化成保守动作 |

**为什么两层 `try/except`？** 外层管"协议解析"，内层管"决策"。
分开是为了让 `state` 可用——内层异常时还能用 `state` 算出保守动作。

## 1.8 主循环：`run()`

```python
def run():
    for raw in sys.stdin:          # ① 逐行读（不是一次读完！）
        raw = raw.strip()          # ② 去掉首尾空白/换行
        if not raw:
            continue               # ③ 空行跳过
        try:
            obj = json.loads(raw)  # ④ 字符串 → 字典
        except Exception:
            continue               # ⑤ 非 JSON（如预热握手）→ 忽略，不崩
        resp, data_out, json_mode = _handle_line(obj)
        if json_mode:              # ⑥ 平台格式 → 回一个 JSON 对象
            out = {"response": resp, "data": data_out, "globaldata": data_out}
            sys.stdout.write(json.dumps(out) + "\n")
        else:                      # ⑦ 调试格式 → 只回整数
            sys.stdout.write(str(resp) + "\n")
        sys.stdout.flush()         # ⑧ 立刻推出去，否则平台会等到超时
```
**① 为什么不用 `sys.stdin.read()`？**
如果平台发完请求后**不关闭** stdin（常驻模式），`read()` 会一直阻塞等 EOF
→ 机器人 8 秒不回复 → 被判"未响应"（真实踩过的坑）。
逐行读在"每轮重启"和"常驻模式"下都能工作。

**⑧ 为什么必须 `flush()`？**
stdout 默认是"行缓冲/块缓冲"。不 flush 的话数据可能留在缓冲区里，
程序还没退出 → 平台读不到 → 超时。

# 第二部分：`game_state.py`（协议解析层）

## 2.1 常量

```python
INIT_CHIPS = 20000        # 每手牌重置的初始筹码
DEFAULT_BIG_BLIND = 100   # 盲注默认（HU 固定 50/100）
```
**为什么要有默认盲注？** 因为平台的 request **不告诉你盲注**。
翻前可以从"我少了多少筹码"反推；翻后（公共牌已发）就没法反推了，
只能用默认值。若这个值错了，只会影响下注尺寸（EV），不会产生非法操作。

### 座位号归一化

```python
try:
    _raw_mid = int(request.get("my_id", 0))
except Exception:
    _raw_mid = 0
try:
    _raw_did = int(request.get("dealer_id", 0))
except Exception:

    _raw_mid -= 1                                            # ④ 1-based → 0-based
    _raw_did -= 1

self.dealer_id = 0 if _raw_did <= 0 else (1 if _raw_did >= 1 else 0)
self.opp_id = 1 - self.my_id                                 # ⑤ 单挑：对手是另一个
```
**为什么需要 ③④？**
有的赛季传"座位 1 / 座位 2"。若不归一化，`my_id = 2` 时
`opp_id = 1 - 2 = -1` —— 而 Python 的 `list[-1]` 表示**最后一个元素**，
于是 `total_win_chips[-1]` 会**静默取错值**（不报错！）→ 锁赢判断全反。
这是一个非常隐蔽的 bug，所以必须显式归一化。

### 牌面编码

```python
self.my_cards = [int(c) + 8 for c in request.get("my_cards", [])]
self.public_cards = [int(c) + 8 for c in request.get("public_cards", [])]
```
**+8 是干什么的？** 平台牌号是 0~51（`点数索引*4 + 花色`）。
内部统一用 `点数*4 + 花色`（点数 2~14）→ 正好差 8。
例：平台 `48`（A♠）→ 内部 `56` = 14*4 + 0。

### 翻前：反推盲注


**核心思路**：我没主动下注，但筹码少了 → 少掉的**就是盲注**。

反推出 `BB = 50` → 锁赢线减半 → 误触发弃牌。加下界钳制后就不会了。


**`_opp_round_known` 是什么？** 标记"我知道对手本轮下了多少"。
对手 all-in 时平台**不给金额**，只能估个上界并标记"未知"，
后面 `to_call` 会走特殊分支。

**`isinstance(a, int) and not isinstance(a, bool)` 为什么这么啰嗦？**
Python 里 `True == 1`，`isinstance(True, int)` 也是 `True`。
如果不排除 bool，某个字段恰好为 `True` 就会被当成"下注 1"。

```python
    self._opp_round_known = not unknown_allin
```
**逐行**：翻后不涉及盲注，直接把本轮动作重放一遍算出各自注额。
`max(rb)` 表示"跟平到当前最大注"。

**「金额未知的全下」**（协议里写 `-2`，没带金额）：与翻前分支同口径 ——
按"对手把剩余筹码推光"处理，直接令 `to_call = 我方剩余筹码`
（`_opp_round_known=False`）。原实现只把它夹到「本轮最大注」→ `to_call`
塌缩成占位 **1** → bot 以为只要跟 1 个筹码 → 任何两张牌都"跟注"、再被
`_normalize` 变成全押（实测：截图第 1 手一对 9 跟掉 19,160）。

### 算 `to_call`

```python
if self._opp_round_known:
    self._to_call = max(0, self.opp_round_bet - self.my_round_bet)
else:
    self._to_call = self.my_chips       # 对手全押金额未知 → 按需全押应对
if self.any_allin:
    self._to_call = max(self._to_call, 1)   # 保证 > 0（不能过牌）
```
**① `max(0, ...)`**：跟注差额不能是负数。
**② 未知时用 `my_chips`**：意思是"要跟就得全下"。
**③ 有人全押时强制 ≥1**：因为规则规定此后不能过牌（`to_call == 0` 会被理解成可过牌）。

### 派生属性（`@property`）

```python
@property
def stage(self):
    return ("preflop", "flop", "turn", "river")[min(self.current_round, 3)]

@property
def to_call(self):
    return self._to_call

@property
def is_button(self):
    """庄家位（heads-up 中庄家=小盲，翻前先行动）。"""
    return self.my_id == self.dealer_id

@property
def pot(self):
    """底池估计 = 双方累计投入之和。"""
    return (INIT_CHIPS - self.my_chips) + (INIT_CHIPS - self.opp_chips)
```
**`@property` 的好处**：调用方写 `state.pot` 就行，不用关心它是存的还是算的；
也不会被误赋值。

### 合法加注边界

```python
def min_raise(self):
    """最小加注数（raise-to 语义）"""
    cur_max = self.my_round_bet
    if self._opp_round_known:
        cur_max = max(cur_max, self.opp_round_bet)
    if cur_max <= 0:
        return self.big_blind        # 本轮无人下注 → 至少下大盲
    return 2 * cur_max               # 否则 → 本轮最大注的 2 倍

def max_raise(self):
    """最大加注数（保守上界）"""
    return max(0, self.my_chips - self._to_call - 1)
```
**为什么 `- 1`？** 平台要求跟注后剩余筹码严格 > 0，所以留 1 的余量最保险。

## 3.1 先验值

```python
_PRIOR = {
    "vpip": 0.68, "pfr": 0.30, "af": 0.35, "fold_to_bet": 0.40,
    "big_raise": 0.25, "turn_aggr": 0.35, "river_fold": 0.40,
}
```
**含义**：还没有数据时，**假设**对手是个"普通玩家"。
样本少时结论偏向这些值，样本多时才相信实测。

## 3.2 贝叶斯收缩：`_shrunk()`

```python
def _shrunk(self, raw, n, key):
    k = 12                                        # 先验权重（相当于 12 个样本）
    return (raw * n + _PRIOR[key] * k) / (n + k)
```
**逐行**
- `raw` = 观测到的比例（如"5 次里弃牌 4 次" → 0.8）
- `n` = 样本数（5）
- 公式 = **加权平均**：实测占 `n` 份，先验占 `k = 12` 份

**算个例子**：`raw=0.8, n=5, prior=0.40`
```
(0.8*5 + 0.40*12) / (5+12) = (4 + 4.8) / 17 = 0.518
```
不会天真地认为"他 80% 会弃牌"，而是 0.52 —— 样本少时更保守。

**为什么用 12 做权重？** 这是调参结果：约等于"12 手牌之后才开始相信实测"。
太小会被噪声带偏，太大则反应迟钝。

## 3.3 风格分类：`archetype()`

```python
        return "unknown"

    af = self.eff_bet_freq()        # ③ 主动下注频率（越大越"凶"）
```

## 4.1 全局状态与哨兵

```python
_OPP_JUMPED = False      # 对手本手是否「突袭大注」
```

## 4.2 刷新全局：`_prepare_globals()`

```python
def _prepare_globals(state, model, ctx, reset_clock=True):
    global _CTX, _OPP_JUMPED, _OPP_BETS_PER_HAND, \
        _DECISION_STARTED_AT, _MODEL_REF       # ① 声明要改这些模块级变量

    _CTX = ctx                                   # ③ 赛制上下文

    try:
        _OPP_BETS_PER_HAND = float(model.avg_bets_per_hand()) \
            if model is not None else 0.9
    except Exception:
        _OPP_BETS_PER_HAND = 0.9                 # ⑥ 对手每手下注次数（窗口均值）
```
**① 为什么一行写不下要用 `\`？** Python 用反斜杠表示"这一行还没结束"。

**为什么要专门抽一个函数？**
`decide()` 入口的锁赢拦截**早于** `_decide_impl()`。
这些全局原本只在 `_decide_impl` 里赋值 → 入口读到的是**上一手的旧值**。
典型后果：`_CTX` 过期 → doomed 判定用的档位偏移差 12 个大盲 → 边界判错。
抽成一个函数、入口和内层都调它，就再也不会不一致。

## 4.3 优势锁定（LEAD_LOCK）：**已于 2026-09-14 移除**

原规则：领先 > 2000（单边 +1000）即"不再全押 + 单次注码 ≤1000"。
**移除原因**：一刀切——三条/坚果领先但未锁胜时面对全下也被强制弃牌
（实测 3 局 55 次面对全下全部 fold，47 次被它拦下）。
其职责已由两条规则替代：
- **主动下注金额**由牌型分级上限管（`_bet_limit`：小两对 2000 / <三条 3000 / ≥三条不限）；
- **面对对手 all-in**由规则2（锁赢硬规则）+ 规则16（局数/对手习惯放宽）+
  翻前分档 / 翻后 `eff_req + margin` 按胜率判定。

## 4.4 锁赢线：`_lock_line()`

```python
def _lock_line(state):
    try:
        from game_state import INIT_CHIPS
        invested = INIT_CHIPS - int(state.my_chips)          # ① 本手已投入
        return 2 * (_blind_line(state, _hands_left(state), own=True) + invested)
    except Exception:
        return 0
```
**公式**：`锁赢线 = 2 × (本手已投 + 剩余手数的盲注线)`

**为什么乘 2？** 我弃牌输 X，对手就赢 X —— 一来一回，**领先差变化 2X**。
所以任何跟"领先差"比较的阈值都必须带这个 2×。

## 4.5 剩余手数：`_hands_left()`

```python
def _hands_left(state):
    try:
        h = int(state.hand_num)
        m = int(state.max_hand)
    except Exception:
        return 0
    if m <= 0:
        return 0
    if h >= m:                      # 兼容 1-based 平台 / 越界
        return 0
    return max(0, m - 1 - h)        # ① 本手之后还剩几手
```
**① 为什么是 `m - 1 - h`？**
平台 `hand` 是 **0-based**（0 ~ max_hand-1）。第 1 手是 `h = 0`，
所以"本手之后"的手数 = `(max_hand - 1) - h`。

**如果不减这个 1 会怎样**（真实事故）：
剩余手数多算一手 → 锁赢线虚高约 300 → **该弃牌保胜时不敢弃，反而继续加注**。
用户截图里"锁赢了还在加注"就是这个原因。

## 4.6 盲注线：`_blind_line()`

```python
def _blind_line(state, hands, own=True):
    try:
        sb, bb = 50, 100                    # ① 平台固定盲注（不用推导值）
        next_my_sb = state.my_id != state.dealer_id   # ② 下一手我是否小盲
        n_sb = (hands + 1) // 2 if next_my_sb else hands // 2
        n_bb = hands - n_sb                 # ③ 分别数小盲局/大盲局
        if own:
            return n_sb * sb + n_bb * bb    # ④ 我全程弃牌的损失
        return n_sb * bb + n_bb * sb        # ⑤ 对手全程弃牌时我能追回的量
    except Exception:
        return int(0.75 * 100 * hands)      # 兜底：平均每局 1.5BB
```
**② 位置每局轮换**：HU 里庄家每手交换，所以"当前是小盲"→"下一手是大盲"。
- `n_sb`：未来 `hands` 手里我当小盲的次数
- `n_bb`：当大盲的次数

**④⑤ 两种视角**
| 参数 | 含义 | 用途 |
|---|---|---|
| `own=True` | 我全程弃牌会损失多少（SB 局亏 50、BB 局亏 100）| 锁赢线（领先方安全线）|
| `own=False` | 对手全程弃牌时我能收多少盲注 | 追回线（落后方能否翻盘）|

**① 为什么硬编码 50/100？** 曾经用 `state.big_blind`（推导值），
在深投入时被推导成 250，导致追回线算成 375（真实 150）→ doom 边界误判。

## 4.7 锁胜判定：`_fold_out_active()`

```python
def _fold_out_active(state):
    try:
        lead = (state.total_win_chips[state.my_id]
                - state.total_win_chips[state.opp_id])   # ① 领先差
        return lead > _lock_line(state)                  # ② 超过锁赢线 → 锁赢
    except Exception:
        return False
```
**逻辑**：领先差 > `2×(本手已投 + 剩余盲注线)` →
即使本手弃牌、之后全程弃牌，仍然领先 → **锁定胜局**。

## 4.8 统一锁赢决策：`_lock_win_unified()`

```python
def _lock_win_unified(state):
    try:
        # A. 防锁赢：数学上追不回 → 只能 all-in 搏
        if _match_adjust(state) == "doomed":
            return {"act": "allin"}

        # B. 锁胜：领先到绝对安全 → 弃牌保胜
        if _fold_out_active(state):
            try:
                if int(state.to_call) <= 0:
                    return {"act": "check"}     # ① 无需跟注 → 不能弃牌，只能过牌
            except Exception:
                pass
            return {"act": "fold"}

        # C. 盈利锁胜：投入过大，输掉就把胜局送人 → all-in
        if not _is_lead_lock(state) and _profit_lock_allin(state):
            return {"act": "allin"}
    except Exception:
        pass
    return None      # 不触发 → 交给常规决策
```
**A / B / C 三个分支**
| 分支 | 含义 | 动作 |
|---|---|---|
| A `doomed` | 弃牌后对手就锁定胜局（追不回）| **全押**搏一把 |
| B 锁胜 | 我已经锁定胜局 | **弃牌**（或过牌）保胜 |
| C 盈利锁胜 | 本手投入太大，输了会被翻盘 | **全押**锁死利润 |

**① 的关键点**：`to_call == 0` 时**不能弃牌**（平台规则），
所以此时用 `check` —— 效果一样（本手不再投入），但一定合法。

**【2026-09-24 补充】**决策出口另有一层「终局效用仲裁」（§4.15）：在
敞口 doom / 投入即锁赢 / 搏命区这些局面里，把弃牌 / 过牌 / 跟注 / 加注 / 全押
放在同一个终局胜率尺度上比较后取最优（只往更保守方向修正）。
A 分支本身仍是无条件全押（弃牌 = 认输）。

## 4.9 兜底动作：`_safe_fallback_action()`

## 4.11 第一道安全网：`_normalize()`

```python
def _normalize(state, action):
    act = action.get("act", "fold")
    to_call = state.to_call
    my_left = state.my_left
    lk_allin = bool(action.get("lk")) and act == "allin"   # 锁赢 allin 免检标记

    # ---- 情况1：本手有人全押（= 我方正面对对手 all-in）----
    if state.any_allin:
        if lk_allin:                        # ① 规则2 锁赢/防锁赢的 allin：免检
            return {"act": "allin"} if my_left > 0 else {"act": "fold"}
        if act == "fold" and _match_adjust(state) == "doomed":
            return {"act": "allin"} if my_left > 0 else {"act": "fold"}
        if act == "fold":
            return {"act": "fold"}
        # ②【2026-09-14 用户规则·替换旧限制】原「翻前跟全下 >1000 → 弃」
        #   与「翻后超牌型上限 → 弃」两条已删除：面对对手 all-in 的定向
        #   决策（规则2 / 规则16 / 翻前分档 / 翻后 eff_req+margin）说了算
        return {"act": "allin"} if my_left > 0 else {"act": "fold"}

    # ---- 情况2：弃牌 ----
    if act == "fold":
        if _match_adjust(state) == "doomed":
            return {"act": "allin"} if my_left > 0 else {"act": "fold"}   # ③
        return {"act": "fold"}

    # ---- 情况3：过牌 ----
    if act == "check":
        return {"act": "check"} if to_call == 0 else {"act": "fold"}      # ④

    # ---- 情况4：全押 ----
    if act == "allin":
        if my_left > 0:
            if lk_allin:                                                  # ⑤
                return {"act": "allin"}
            if _over_limit(state, my_left):
                if to_call > 0 and to_call >= my_left:                    # ⑥
                    return {"act": "allin"}       # 跟注即全下：放行
                num = PREFLOP_MAX_BET             # ⑦ 主动 shove：仍降级
                ...
            return {"act": "allin"}
        return {"act": "check"} if to_call == 0 else {"act": "fold"}

    # ---- 情况5：跟注 ----
    if act == "call":
        if to_call <= 0:
            return {"act": "check"}                                       # ⑧
        if to_call >= my_left:
            return {"act": "allin"}                                       # ⑨
        return {"act": "call"}
```
**逐条解释**
| 编号 | 规则 | 原因 |
|---|---|---|
| ①⑤ | 锁赢类 allin 免检直通 | 【2026-09-14 方案1】规则2 是硬规则：ctx 保守偏移使 `_match_adjust` 不是 doomed 时，旧代码会把 doom / 盈利锁胜的 allin 降级成 fold |
| ② | 有人全押时不再设 allin 金额/牌型限制 | 【2026-09-14 用户规则】面对对手 all-in 的定向决策替换所有旧 allin 限制 |
| ③ | doomed 时弃牌升级为全押 | 弃牌 = 直接认输 |
| ④ | `to_call > 0` 时不能过牌 | 必须跟/加/弃 |
| ⑥⑨ | 跟注即全下 → allin | 同属面对对手 all-in 的定向决策（赔率/牌力已判定） |
| ⑦ | **主动**全押超上限 → 降级为上限加注 | 我方主动大额投入仍受牌型分级节制 |
| ⑧ | 无需跟注 → 跟注变过牌 | 等价且合法 |

**"lk 标记"是什么？**
`_lock_win_legal()` 把锁赢动作交给 `_normalize` 之前，给 allin 打上内部标记
`{"act": "allin", "lk": 1}`。`_normalize` 见到标记即直接放行——保证规则2
（锁胜 / 防锁赢）的结论不会被金额或牌型上限推翻。标记只在本函数内部使用，
返回给平台的动作都是干净的新 dict。

**整体设计**：决策层可以"想得很激进"，输出层一定"很保守"。
即便策略有 bug，也不会产生非法动作被判负。

## 4.12 搏命区与牌力分流：`_gamble_zone` / `_gamble_plan`（规则18）

**用户规则（2026-09-16）**：
> 「对方快锁赢时应该是开局就 allin」→ 补充为「牌好就多过牌再 allin，不好就开局 allin」

落后到**几乎追不回**（但还没越过 doom 线）时，这一手必须搏——但**怎么搏取决于牌力**。

### 触发：`_gamble_zone()`

```
lead < 0  且  lead ≤ −GAMBLE_LINE_FACTOR(0.95) × 2×_blind_line(剩余手数, own=False)
```

即「追赶余地只剩 5%」的灰区。越过线（≥1.0）由规则2 doom 接管（无条件 allin），
本函数只管这段灰区。`lead` 与追平线在一手之内不变 → **一旦进区，整手都在区内**，
这正是「可以慢慢过牌、最后再 all-in」的前提。

### 牌力：`_gamble_hand_good()`

| 阶段 | 「牌好」判定 |
|---|---|
| 翻前 | 起手牌百分位 ≤ `GAMBLE_GOOD_PCT`（默认 top 20%：77+ / AK / AQ 这一档） |
| 翻后 | 有效牌型 ≥ 两对 ／ 坚果级或强听牌（`_has_nuts_or_strong_draw`）／ 一对且为顶对·超对（`_pair_is_top`） |

判定全部是**确定性**的（不使用 MC），避免抽样抖动让同一副牌忽好忽坏。

### 分流：`_gamble_plan()`

| 牌力 | 局面 | 动作 |
|---|---|---|
| 牌烂 | 任何街 | **all-in**（开局梭哈，逼对手用整副筹码接 50/50） |
| 牌好 | 能过牌（`to_call == 0`） | **check**（过牌诱敌） |
| 牌好 | 翻前只需补大盲 | **call**（溜入看翻牌，翻前版的「过牌」） |
| 牌好 | 对手已加注／已下注 | **all-in**（收网） |
| 牌好 | 河牌且免费 | **all-in**（最后一条街，不再等） |

`allin` 带 `lk` 标记 → 免检，不会被翻前 1000 / 翻后牌型上限降级成加注。

**为什么烂牌要越早越好**：等到河牌才 all-in，对手只投了一点点、随手弃牌我们
只赢个小池（弃牌权益≈0）；开局 all-in 才能让对手用整副筹码陪我们 50/50。

**调参入口**：`GAMBLE_LINE_FACTOR`（进区门槛，默认 0.95）、`GAMBLE_GOOD_PCT`
（翻前「牌好」阈值，默认 0.20；调小 = 更多牌被当烂牌直接梭）。

## 4.13 对手「吓不走」→ 停用小注：`_small_bet_futile`（规则19）

**用户规则（2026-09-16）**：
> 「遇到下小注吓不走的对手（指运用这种策略时对手很少弃牌），不要再下小注了」

小注的收益来自**弃牌权益**。对手几乎不弃，小注就只剩代价（底池做不大、还被反打）。

### 判定

```
对手面对我方小注（≤40% 池 = opponent 的 sf_s 尺寸桶）的反应样本 ≥ 4
且 弃牌率 < SMALL_BET_FOLD_MIN(0.35)  →  True
```

样本不足或翻前 → `False`（不改变行为，避免前期误伤）。数据来源就是
`opponent.bet_resp_stats(_BUCKET_SF_SMALL, hand, 4)` —— 我方每次下注后对手
弃/跟/加都会被记进窗口。

### 命中后作废的小注路线

|---|---|---|---|
| 规则12 过牌后小注 | `_opp_check_bet` | 30~45% 池 | 过牌 |

## 4.15 终局效用仲裁：`_endgame_arbitrate()`（2026-09-24 用户规则）

**背景（实战第51手 = 对局日志 `hand=50`）**：河牌 9♦A♠8♠6♠7♦，我方 A♦4♣（一对 A），
对手 6♣9♥（两对）。我方过牌 → 对手只下注 **192** → 我方却 **all-in 19,600** → 被跟
→ 输掉整场。

**【关键口径】牌面/界面上的「底池 20,592」是 all-in 之后的显示值**（992 + 19,600）。
决策时底池只有 **992**：

| 项 | 值 |
|---|---|
| 底池 / 需跟 | 992 / 192（对手注 = 19% 池） |
| 本手已投 / 我方剩余 | 400 / 19,600（需跟仅占筹码 **0.98%**） |
| 本手盈亏 / 剩余手数 | 落后 914 / 19 手（追回线 1450） |
| 弃牌口径 | −1828 − 2×400 = −2628 **>** −2900 → 不 doom（弃牌安全）|
| 跟注口径 | −1828 − 2×592 = −3012 **≤** −2900 → doom（**余量仅 112 筹码**）|

### 为什么重写（用户指出的结构问题）

用户原话：「**不是先决策再改吧？而是在决策时就要同时考量弃牌的价值，而不是决策
加注后改成全压**」。

旧结构是两个「改写动作」的单向补丁：

| 旧补丁 | 行为 | 问题 |
|---|---|---|
| `_doom_call_upgrade` | call/raise → **allin** | 只会更激进；决策层完全不知道 doom 存在 |
| `_doom_bet_downgrade` | raise → **check** | 方向相反，但同样是事后覆盖 |

两者都**不曾把「弃牌」作为候选**参与比较 —— 而第51手里弃牌本身是安全的
（只损失 400，且弃牌后并未被锁死）。

### 新结构：把「最终赢下比赛的概率」当统一尺度

```python
def _win_utility(state, lead_after):
    """lead_after → 最终胜率 U ∈ (0,1)：锚点为赛事两条硬线（±2×_blind_line），
    中间用 logistic 平滑过渡（UA_SLOPE=1.6，差一条硬线 ≈ 1σ）。"""
    scale = max(2*_blind_line(hl, own=True), 2*_blind_line(hl, own=False), 1)
    return 1 / (1 + exp(-UA_SLOPE * lead_after / scale))
```

**关键：不做「线上 1、线下 0」的悬崖**。两条硬线是「只靠收盲注」的最坏界，
不是真实胜率；用悬崖会让 bot 在擦线处孤注一掷（第51手只越线 112 筹码）。

然后给每个候选动作算期望效用 `EU = Σ P(分支) × U(结算后的 lead)`：

| 动作 | 分支 |
|---|---|
| fold / check | 1 条：`lead − 2×已投` |
| 跟注 E | 赢 `lead + 2×(底池 − 已投)`；输 `lead − 2×(已投 + E)` |
| 加注/全押 n | 对手弃（概率 f=弃牌权益）→ 收池；对手跟 → `eq_c×U(赢大池) + (1−eq_c)×U(输更多)` |

其中 **`eq_c = eq^(1 + UA_CALL_DAMP×n/底池)`**（UA_CALL_DAMP=0.6）：注额相对底池越大，
肯跟的范围越窄 —— 「20 倍超池全押被跟 = 我们大概率已经输了」。
用**幂次**而非乘系数：`eq=1`（坚果/四条）时 eq_c 仍为 1（跟注范围同样被我们统治）。
对手已全押时 `f=0`（他没有弃牌分支）。

### 四条护栏（按执行顺序）

1. **`UA_CROSS_CHECK`（用户硬规则·09-15 方案B）**：有免费过牌且「投进去就越线」
   → 直接**过牌**（约束，不交给效用模型权衡）。
2. **`UA_SEALED_ALLIN`（用户硬规则·防锁赢，2026-09-24）**：**越线 → 无条件全押**。
   判据 `_sealed_by_call`：`lead − 2×敞口 ≤ −2×追回线 ×(1+UA_SEALED_MARGIN)`，
   即「再投这笔、输掉就把胜局送出去」且**明显越线**（默认 ≥15% 幅度）。
   · 实战第32手：越线 3,458（追回线的 61%）→ 全押 ✓（用户：「越线就全压是合理的」）
   · 实战第51手：只越线 112（3.9%）→ 视作「擦线」不触发（跟注很便宜、弃牌也没被锁死）
   · 把 `UA_SEALED_MARGIN` 设为 0 = 只要越线就全押。
3. **只往「少冒风险」方向修正**（`UA_RISK_RANK`：fold/check < call < raise < allin）：
   效用比较可以「加注→跟注」「跟注→弃牌」，但**不制造新的加注/全押**。
4. **硬性弃牌不被翻案**：河牌公对陷阱、突袭大注、公对风险规避等返回的 fold
   属于低档位，仲裁不会把它升成 bet。

> **顺序为什么这么排**（用户 2026-09-24 指出第51手的问题就是顺序）：
> 先判「**弃牌会不会被锁赢**」（入口规则2-A；会 → 无条件全押），再判「**继续投入
> 会不会越线**」（这里 ②）；只有在两者都不是硬约束时，才轮到效用比较。
> 第51手正是「弃牌安全 + 只是擦线」，所以不该被硬压成全押。

**触发面**（`_endgame_matters`）沿用旧补丁：敞口 doom / 投入即锁赢 / 搏命区。
不触发时**原样返回决策层结果**，普通局面（早中期、不涉及锁赢）完全不受影响。

### 第51手实测（EU）

```
弃牌 0.190 ｜ 过牌 0.190 ｜ 跟注 0.286 ｜ 加注(576) 0.322 ｜ 全押 0.188
```

全押的期望胜率**最低**（超池全押只剩更强的牌跟），仲裁因此不会再产生它。

**调参入口**：`UA_ON`（总开关）、`UA_SLOPE`（U 的陡度）、`UA_CALL_DAMP`（被跟时 eq 收窄）。

## 4.16 大额投入闸门：`_big_money_guard()`（规则20，2026-09-24）

**背景（实战第21手 = 对局 log `hand=20`）**：河牌 10♠6♦A♣3♥K♦，我方 8♣6♣（一对 6，
最小对子），对手 8♦A♦（一对 A）。对手加注至 **6,318**（1.14 池），我方**全押 17,226**
→ 被跟 → 输掉。

**筹码复原（与截图完全吻合，是本轮定位的关键）**：

| 项 | 值 |
|---|---|
| 底池 / 需跟 | 11,866 / 6,318（需胜率 34.7%） |
| 本手已投 / 剩余 | 2,774 / 17,226 |
| 反推手牌开始时的筹码 | 17,226 + 2,774 = **20,000**；对手 10,908 + 2,774 + 6,318 = **20,000** |
| ⇒ 本场 | **0:0**（不是 doom，也不在搏命区） |
| 跟注口径 | −18,184 ≤ −7,400（越线 **146%**）→ `UA_SEALED_ALLIN` 触发 |

即：全押来自「跟注即明显越线 → 无条件全押」，而它的前提是**决策层原本想跟注**
（`chip_action ∈ {call, raise}`）—— 那一步是**对手模型**的功劳：
判定为 maniac（`eff_req −0.08`）＋ 规则16 放宽（最多 −0.09）＋ 被动型（−0.02）叠加后
门槛可低到 ~0.20，而一对 6 的 MC 胜率约 0.21（若把对手范围估到 67%，甚至能到 0.49）
→ 刚好越过 → call → 被升级成全押。

```python
def _big_money_guard(state, action):
    act, to_call, my_left = action.get("act"), int(state.to_call), int(state.my_left)
    if state.any_allin or to_call >= my_left:
        return action                     # 豁免：应对对手全下（定向决策）
    strong = _strong_for_big_money(state)  # 翻后 ≥三条 / 翻前 AA·KK·QQ·JJ·AKs
    if act == "allin":
        if strong:
            return action
        if to_call <= 0:
            return {"act": "check"}
        return {"act": "fold"} if to_call > BIG_CALL_LIMIT else {"act": "call"}
    if act == "call" and to_call > BIG_CALL_LIMIT and not strong:
        return {"act": "fold"}
    return action
```

| 规则 | 条件 | 动作 |
|---|---|---|
| R1 | `to_call > 3000` 且 有效牌型 < 三条 | **fold** |
| R2 | **主动**全押仅在 [≥三条 / 翻前超强牌] 时允许 | 否则降级 |

- **豁免**：`any_allin` 或 `to_call ≥ my_left`（应对对手全下）→ 原样放行
  （2026-09-14 用户规则：针对对手 all-in 的定向决策替换所有旧限制）。
- **不经过本闸门的两条路**：规则2-A 防锁赢（弃牌即锁死 → 入口无条件 allin）、
  规则18 搏命区 —— 它们在 `decide` 入口就 `return`，所以「该搏命时」不会被削弱。
- **放置位置**：`_decide_impl` 出口的**最后一步**（在 `_endgame_arbitrate` 之后）——
  仲裁的升级动作带 `lk=1` 免检标记，必须在它之后再收紧。

**调参入口**：`BIG_CALL_LIMIT`（默认 3000）、`BIG_MONEY_GUARD_ON`（总开关）。

# 附录：常见"看不懂"的写法速查

| 写法 | 含义 |
|---|---|
| `a, b = 50, 100` | 同时给两个变量赋值 |
| `x or y` | `x` 为假（0/None/""/[]）时取 `y` |
| `x if cond else y` | 三元表达式：cond 为真取 x，否则取 y |
| `lst[-1]` | 倒数第一个元素（**危险**：越界不报错，会静默取错）|
| `obj.get(k, default)` | 取字典键，缺失时返回 default（不报错）|
| `for i, v in enumerate(lst)` | 同时拿到下标 `i` 和元素 `v` |
| `reversed(lst)` | 倒序遍历 |
| `isinstance(x, int)` | 判断类型 |
| `max(0, x)` | 把负数钳成 0 |
| `try/except` | 出错就走 except（本项目大量使用做防御）|
| `global X` | 在函数内修改模块级变量 X |
| `@property` | 让方法能像变量一样读取 |
| `object()` | 创建一个独一无二的对象（常做哨兵）|
| `\\`（行尾反斜杠）| 语句换行继续 |
| `f"{x}"` / `"%s" % x` | 字符串格式化（本项目用后者）|
