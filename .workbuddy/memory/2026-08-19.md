## 修正：找到了"第一步非法"的真正根因

用户上传 BotZone 对战截图，显示错误为 **"INVALID INPUT VERDICT"**（BB 位置翻牌前被判负）。这给了一个关键线索——**bot 的输出被判非法输入**。

之前判断简单交互输出 JSON 动作是错的。**BotZone 简化模式（简单交互）的输出是纯文本，不是 JSON**：

> 简化模式：如果不需要 data/debug，直接输出纯文本即可，例如 `3 5` 等价于 `{"response": "3 5"}`

德州扑克简单交互下，输出必须是**纯文本一行**：
- `fold` / `check` / `call` / `allin`
- `raise <num>`（如 `raise 250`）

### 最终修复
- `bot.py` 简单交互分支改为 `sys.stdout.write` 纯文本（`raise 250` 而非 JSON）。
- JSON 交互分支保持包装格式。
- 重新 `bundle.py` 生成 `botzone_submit.py`（965 行）。

## 重大重写：拿到官方协议后彻底重写

用户提供了 BotZone 德州扑克**完整官方规范**，之前所有假设（牌编码、状态字段、response 格式、交互模式）全部错误。已彻底重写。

### 官方协议关键点（务必牢记）
- **牌**：0~51 整数。点数 = n//4+2（2~14，14=A），花色 = n%4（0=红桃,1=方块,2=黑桃,3=草花）。内部编码沿用「点数*4+花色」= **n+8**，这样 evaluator/ranges 的 `c//4`(点数)、`c%4`(花色) 逻辑不变。
- **Request**（只支持 JSON 交互）：`num_players/dealer_id/my_id/my_chips/my_cards/public_cards/history/hand/max_hand/total_win_chips/total_win_games`。无 blind/pot/curbet 字段，需从 history 重建。
- **Response 是单个整数**：`-1`=fold，`-2`=allin，`0`=call/check，`>0`=raise 的**纯加注量**（跟平之外的额外下注）。
- **最小加注**（纯加注量）：首位加注 >= 大盲(100)；再注 >= 本轮最大纯加注量的 **2 倍**。
- **每步 1 秒限时**。
- **盲注固定 50/100，初始筹码 20000**（硬编码于 game_state.py 顶部）。

### 重写内容
- `game_state.py`：全新，从 request + history 重建牌局（盲注→逐条 history 累积，raise=跟平+纯加注，跨轮重置 cur_max_raise）。派生 to_call/pot/stage/位置/min_raise/max_raise。
- `bot.py`：读 request JSON → 决策 → 输出整数 response（`sys.stdout.write(str(resp))`）。
- `strategy.py`：`_raise_to` 改为「目标总投入→纯加注量」转换；`_normalize` 安全程序用 min_raise/max_raise。
- `opponent.py`：`build_model_from_history` 直接读 history 的 action_type 统计对手动作（无需推断）。

## 第二次重大修复：JSON 交互包装 + raise-to 语义（真正的开局非法根因）

用户反馈重写后**开局仍然非法操作**，并要求全面复查根因。分析官方规则文本 + BotZone 通用交互规范后找到两个致命问题：

### 根因（按重要性）
1. **I/O 包装不匹配（主因）**：该游戏"与 BotZone 其他游戏一样使用 Bot#交互，只支持 JSON 交互"——输入是 `{"requests":[...], "responses":[...], "data":..., "globaldata":...}` 包装（requests 元素是 request 的 JSON 字符串或对象），输出必须是 `{"response": <int>, "data":..., "globaldata":...}`。原 bot.py 把 stdin 整体当裸 request 解析 → `my_cards` 缺失 → 崩溃；且输出裸整数 → INVALID INPUT。
2. **raise 整数语义**：规则"下注筹码不少于上一位在场玩家下注筹码的 2 倍"+"首位加注不少于大盲注"指向 **raise-to 语义**（数字=加注后本轮总注额，如对手下100我加注到200），而非"纯加注量"。原开池输出 150 在任何解读下都 < 最小加注。
3. **规则5未实现**：本局有人全押后只能返回 -1/-2，其余一律非法。
4. **对手建模重复计数**：平台每回合重放完整 history，原实现每次全量累加导致重复统计。

### 修复内容
- `bot.py` 重写：解析 JSON 交互包装（requests[-1] 兼容字符串/对象），输出 `{"response":int,...}` 包装；裸 request 走本地调试模式输出裸整数；任何异常都有兜底（能过牌就0、能跟就0、否则-1），加 `_final_guard` 整数级安全网（规则5、跟注需 my_chips>to_call 严格大于、加注夹紧 [min,max) 越界转全下）。
- `game_state.py` 重写为**盲注无关的合法性推导**：翻前 my_round_bet = 20000-my_chips，to_call 由对手本轮最后一个动作（raise→数字即其总注额 / call、check→已跟平 / allin→只能弃牌全押）；翻后只重放当前轮 history。盲注动态推导（SB首次行动：SB=20000-my_chips、BB=2SB；BB等选项：BB=my_total_in），仅影响下注尺寸不影响合法性——即使盲注假设错误也绝不非法。
- `strategy.py`：`_raise_to` 改 raise-to 语义；`_normalize` 加规则5全押限制；蒙特卡洛加 0.6s 软时限（`TIME_BUDGET`）。
- `opponent.py`：`OpponentModel` 增加 `last_hand`/`last_opp_count` 字段做跨回合去重，换手牌自动清零，画像经 globaldata 跨手牌持久化。
- 新增 `test_e2e.py`：多回合端到端测试（11 项，含持久化去重、损坏输入兜底、计时）。

### 关键协议结论（覆盖之前的错误记忆）
- **输入输出都是 JSON 包装**，不是裸 request/裸整数！
- **raise 语义 = raise-to（本轮总注额）**，min = 2×本轮最大注额（翻前含盲注），首位下注 ≥ 大盲。
- **盲注 100/200**（依据：官方示例 my_chips=19800 = 20000-200 且 BB 无主动投入；此前记的 50/100 属于另一个旧游戏）。合法性推导已盲注无关，此假设仅影响尺寸。
- 每手牌筹码重置 20000（由 total_win_chips 累积 vs my_chips=20000-invested 推断证实）。
- 加注数值同时满足 ≥2×最大注额 → 即使 raise-to 判读有误（实际是增量语义）也依然合法，只是尺寸偏大。
